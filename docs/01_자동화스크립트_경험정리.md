### 1-1. 커널 리비전별 장기 안정성 A/B 검증 체계

**설계 핵심 — 실험 설계로서의 자동화**
- **IP 대역 = 커널 리비전 그룹** 매핑 규칙을 코드에 명시하여, 4개 커널 리비전(rev19 / rev160 / rev202 / rev247)을 **각 9~10대씩 동시 장기 소킹**하는 A/B 테스트를 설계했습니다.
- 단순 스크립트가 아니라 **"어떤 커널이 더 오래 안 죽는가"를 통계적으로 답하기 위한 실험 인프라**입니다.

**기술적 포인트**
- `expect` 인라인/heredoc 동적 생성(`/tmp/expect_${ip}.exp`)으로 telnet 대화형 세션 자동화
- **46개 서브셸 병렬 실행 + `wait` 동기화** → 순차 telnet 대비 실행시간 수십 배 단축
- **공유 결과 파일 집계 패턴**: 각 워커가 `printf "%-10s %-20s %s"` 정렬 포맷으로 append → `sort`로 그룹 정렬 출력
- `tr -d '\r'`(telnet CR 제거), `grep -E 'up +[0-9]'`(파싱 방어), `set timeout 5` + 무응답 폴백

### 1-2. 커널 로그(dmesg) 자동 수집 및 이상 감지 ★

| 스크립트 | 역할 | 줄수 |
|---|---|---|
| `yh_utility/telnet_dmesg.sh` | 순수 expect 스크립트로 타깃 `dmesg` 전량 파일 저장 | 25 |
| `yh_utility/settingenviron.sh` | 46대 dmesg 수집 → **부팅 이후 발생한 이더넷 link flap만 자동 검출** | 130 |

**설계 핵심 — 노이즈와 진짜 결함의 분리**
- 부팅 과정에서 정상적으로 발생하는 link up/down과, **운영 중 발생한 비정상 링크 플랩**을 구분하는 것이 목적이었습니다.
- `BOOT_THRESHOLD=60` — **커널 타임스탬프 60초를 경계로 부팅 노이즈를 필터링**하는 휴리스틱을 도입.

- 로그 파일 부재 / link 이벤트 부재 / 이상 검출을 **3단 분기**로 처리.

**실증 자료**: `yh_utility/dmesg_logs/dmesg_192.168.235.11.log` ~ `.56.log` **46개 파일(각 15~16KB) 실제 수집 완료**

### 1-3. 원격 시스템 부하(스트레스) 테스트 프레임워크

**`yh_utility/EN675_SYSTEM_LOAD_TEST/run_remote_stress.py`** (78줄, Python `telnetlib` + `threading`)

20대 카메라에 **CPU / Memory / Network 부하를 동시 인가**하고 일괄 해제하는 오케스트레이터.

| 부하 종류 | 인가 방식 |
|---|---|
| CPU | `dd if=/dev/urandom of=/dev/null & PID=$!; sleep N; kill $PID` (자기 종료형) |
| MEM | `mount -t tmpfs -o size=50M` 램디스크 생성 → 50MB 채움 → `umount` |
| NET | `iperf -s -t N &` |
| 정지 | `killall dd iperf` |

- **스레드 병렬 + 스태거링**: 장비당 스레드 기동, `time.sleep(0.1)`로 접속 폭주 완화 후 `join()` 수렴

- `with telnetlib.Telnet(...)` 컨텍스트 매니저 + 장비별 try/except → **개별 실패가 전체 실패로 전파되지 않음**

## 8. 갭 분석 및 보완 전략

### 갭 1: ftrace / perf / trace-cmd / eBPF (필수 요건)

PC 전체 조사 결과 **ftrace·perf 기반 커널 프로파일링 스크립트가 발견되지 않았습니다.** 이는 공고의 필수 요건이므로 정면 대응이 필요합니다.

**보완 전략**
1. **인접 경험으로 연결** — 보유한 것은 "커널 내부 프로파일링"은 아니지만 **성능을 정량화하는 방법론 자체**는 확립되어 있음:
   - `measure.py`의 `sync` 포함 측정 → **페이지 캐시 flush까지 고려한 I/O 완료 시간 측정** 개념 이해
   - `settingenviron.sh`의 **커널 타임스탬프 파싱** → dmesg 시간축 분석 경험
   - FreeRTOS **Percepio TraceRecorder 스냅샷 트레이싱** 경험(`coding/freertos_qemu_demo/CLAUDE.ko.md`)
     → `dump binary value trace.bin *RecorderDataPtr` — **트레이싱 도구로 스케줄링 동작을 관측한 경험**으로 서술 가능
2. **마감(8/10)까지 실습 후 추가** — 보유 환경(Jetson/QEMU)에서 `perf record/report`, `ftrace function_graph`, `trace-cmd` 실습을 짧게라도 수행하고 결과를 문서화하면 "도구 사용 경험 있음"으로 서술 가능. **freertos_qemu_demo 환경이 이미 구축되어 있어 진입 비용이 낮습니다.**

## 9. 자기소개서 초안 문장 (그대로 쓰거나 다듬어 사용)

> **[자동화로 검증 규모를 늘린 경험]**
> IP 카메라 펌웨어의 커널 안정성을 검증할 때, 사람이 장비를 하나씩 telnet으로 접속해 확인하는 방식으로는 유의미한 표본을 얻을 수 없다고 판단했습니다. 이에 expect와 bash 병렬 처리를 이용해 **46대 장비를 동시에 제어하는 테스트 팜을 구축**하고, IP 대역별로 커널 리비전 4종을 9~10대씩 배정해 장기 소킹 A/B 검증 체계를 설계했습니다. 46개 워커가 공유 결과 파일에 정렬 포맷으로 집계하는 구조로 만들어 순차 실행 대비 수십 배 빠르게 전수 점검이 가능해졌습니다.

> **[로그에서 진짜 결함만 골라낸 경험]**
> 46대에서 수집한 dmesg를 사람이 읽는 것은 불가능했고, 더 큰 문제는 부팅 시 정상적으로 발생하는 이더넷 link up/down이 노이즈로 섞인다는 점이었습니다. 커널 타임스탬프를 PCRE로 파싱해 **부팅 후 60초를 경계로 노이즈를 필터링**하고, 그 이후 발생한 링크 플랩만 승격 출력하도록 자동 판정 로직을 구현하여 실제 결함만 검토 대상으로 좁혔습니다.

> **[성능을 숫자로 만든 경험]**
> 장비의 AI 모델 로딩이 느리다는 정성적 보고를 정량화하기 위해, `tar -zxf`와 `tar -zxvf`의 해제 시간을 파일 크기별로 비교하는 벤치마크를 자동화했습니다. 정확한 측정을 위해 **`sync`를 붙여 페이지 캐시 flush까지 포함한 실제 쓰기 완료 시간**을 재고, 매 측정 전 집합 차분 기반 클린업으로 동일 시작 조건을 보장했습니다. verbose 터미널 I/O가 만드는 오버헤드를 %로 산출해 CSV 리포트로 남겼습니다.

> **[취약점을 닫고 확인한 경험]**
> CodeQL로 자사 펌웨어(goahead 6.1.0)를 분석해 **TOCTOU 취약점 4건을 탐지**했고, `stat()` 후 `open()`하는 패턴을 `open(O_NOFOLLOW)` 후 `fstat()`로 수정한 뒤 **재스캔으로 4건 → 2건까지 감소를 검증**했습니다. 또한 레거시 C 코드베이스 전반의 `strcpy`·`sprintf` 등 위험 함수는 Coccinelle 시맨틱 패치 244줄을 작성해 경계검사 래퍼로 일괄 치환하여, 수작업 없이 트리 전체에 재현 가능한 형태로 적용했습니다.
